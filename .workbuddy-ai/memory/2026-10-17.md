## Backend rebuild exposed a LATENT BUILD BUG — how to build/run the backend

After the keyboard work I rebuilt `dist` and `node dist/main` crashed with
`Cannot find module 'src/database/schema/sTransaction.schema'`.

**Root cause (pre-existing, not caused by the keyboard change):** 38 imports across 15 backend files use
absolute specifiers like `import { X } from 'src/database/schema/...'`. TypeScript resolves those at
compile time via `baseUrl: "./"` but emits them **verbatim** as `require("src/...")`, which Node cannot
resolve. The previously running `dist` was stale (built Oct 16 09:54, before those imports were added),
which is the only reason the app worked. **Any fresh build of this repo is broken at runtime.**

**Workaround in place (no source changes):** `backend/tsconfig.paths.json` maps `src/*` → `dist/*`, and
the backend is launched with runtime path resolution:

```bash
cd backend
npx tsc -p tsconfig.build.json          # NOT `nest build` — deleteOutDir trips the safe-delete guard
TS_NODE_PROJECT=tsconfig.paths.json node -r tsconfig-paths/register dist/main
```

`npm run start:prod` (`node dist/main`) **will fail** on any fresh build until the imports are fixed.

**Permanent fix (not applied):** rewrite the 38 `'src/...'` imports to relative paths, then
`npm run start:prod` works normally. Mechanical but touches 15 files.

**Current running state:** backend PID 24424 on :3000, bot **@BingoRushBot** (id 8219023295).

## Running the app with NO file edits (env-override technique)

Because `backend/src` reads `process.env.ORIGIN` / `process.env.TELEGRAM_WEBAPP_URL` directly and dotenv
does **not** override already-set vars, config can be changed per-launch on the command line — no need to
edit `.env` (which matters when the user says "don't touch the code"). `backend/.env` was left untouched
(it still points at an old dead tunnel) while the running process used the new values.

```bash
# backend (note: NOT `npm run start:prod`, see the build-bug section above)
cd backend
ORIGIN=https://<frontend-tunnel> \
TELEGRAM_WEBAPP_URL=https://<frontend-tunnel> \
TS_NODE_PROJECT=tsconfig.paths.json node -r tsconfig-paths/register dist/main

# frontend — vite.config `define` reads process.env.VITE_API_URL from the shell
cd ..
VITE_API_URL=https://<backend-tunnel> npm run dev:frontend
```

Order matters: start both cloudflared quick tunnels **first** so the frontend origin is known before the
backend boots (CORS `ORIGIN` must equal it exactly, since axios uses `withCredentials`).

Full checklist to verify a run: both ports listening, both tunnels 200, `<title>` present through the
frontend tunnel, the backend tunnel URL present in the served `/src/services/api.ts`, and an OPTIONS
preflight returning `Access-Control-Allow-Origin: <frontend tunnel>`.

**Gotcha:** quick-tunnel hostnames change on every restart, so all of `ORIGIN`, `TELEGRAM_WEBAPP_URL`
and `VITE_API_URL` must be updated together each time.

**Still true and worth remembering:** the Mini App cannot render outside Telegram —
`src/services/telegram.ts:91` throws `LaunchParamsRetrieveError` from an unguarded field initializer — so
opening the tunnel URL in a plain browser shows a blank page. Testing must happen inside Telegram.
